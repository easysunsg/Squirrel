# 草莓连续对话问题分析与修改计划

## 1. 结论摘要

这段对话暴露的不是单个提示词问题，而是四类系统性缺陷：

1. 入库回复按“记录数”计数，不能表达“2 盒”；
2. 备注没有正式意图、实体和数据库操作，成功回复可能只是分类器/模型生成的表面结果；
3. 后续省略主语时，没有可靠地把“草莓”作为当前批次和操作目标，保质期更新因此可能误改牛奶；
4. 搜索和消耗没有落实用户给出的范围、品类、容器和数量约束。

最终结果是：用户看到的回复声称操作成功，但库存状态可能未改变、改变了错误物品，或查询返回了不满足条件的物品。这属于数据正确性问题，优先级高于措辞优化。

## 2. 逐轮问题与代码依据

### 2.1 “两盒草莓”回复成“1 件物品”

用户表达的是一个草莓批次，数量为 2 盒。解析器会生成一个 `Item` 记录，`count=2`、`unit=盒`，这本身是合理的批次建模；但聊天层使用 `len(parsed_items)` 作为数量，因而把一条记录报告成 1 件。确认接口同样使用 `len(created)` 拼接“已新增 1 件物品”，没有展示总数量。

相关位置：`app/services/graph.py` 的 add 分支、`app/api/routes.py` 的 `confirm_items`、`app/services/parser.py` 的 `parse_lightning_text`。

影响：用户无法确认系统是否识别了“2 盒”，也会误以为只录入了一盒。后续扣减应以 `count` 为准，而不是以记录条数为准。

### 2.2 “每盒 500 克，加备注”没有可执行能力

`ChatIntent` 目前只有 `update_location`、`update_expiry`、`update_remaining` 等更新类型，没有 `update_remark`；`ChatOperation` 的 patch 虽然是开放字典，但 parser、parameter resolver、InventoryCapability 都没有为 remark 定义解析和执行路径。数据库 `Item` 有 `remark` 字段，说明存储层具备字段，但 API 没有把自然语言变更映射到该字段。

因此这轮如果返回“备注已加上”，不能证明数据库真的更新。即使模型把话术生成得很肯定，`extended_to_old_dict` 只有收到有效 mutation log 才会产生 `upsert_items`，没有 mutation log 就不会写入。

### 2.3 “保质期一般是 3 天”误更新牛奶

规则函数 `extract_expire_patch` 只处理“保质期延 N 天”、明确日期和“明天过期”，不处理“保质期是/一般是 N 天”。`extract_target_title` 也不能从这句省略主语的话中提取草莓。

更新节点最终按 `item.title == target` 选中第一条同名记录；预执行检查也只做同样的精确标题匹配。换言之，目标必须在分类阶段已经正确解析，否则执行层没有办法纠正。

会话状态只持久化 `last_added_item` 和单个 `current_context_item`。确认入库时只保存 `last_added_item`；中间查询还可能把 `current_context_item` 改成其他物品。没有“最近一次已确认批次”的不可变焦点、来源轮次和操作锁定机制时，“保质期”这类缺主语的补充句很容易落到旧上下文（例如牛奶），出现“牛奶的保质期已更新”。

### 2.4 “冷藏层里别的盘装生鲜”返回胡萝卜和牛奶

`query_handler_node` 的 `search_query` 调用 `match_search_items`。该函数先调用向量搜索，只要向量返回结果就直接返回，不再执行位置、类别或容器过滤。规则回退也只把关键词与 `title/location/spaceName/remark` 做字面包含匹配，模型中没有“盘装”“生鲜”这两个可过滤的结构化字段。

因此用户要求的至少三个约束（冷藏层、盘装、生鲜/食物）没有被建模。返回胡萝卜和牛奶只能说明语义相似或关键词命中，不能说明它们满足问题范围。

### 2.5 “草莓洗一盒下午吃”没有可靠扣减

规则消耗触发词包括“吃完、用完、用了、吃了、吃掉、一半”等，但不包括“洗一盒”“下午吃”这种计划性消耗表达。`extract_target_title` 也没有“洗一盒”模式，数量扣减解析只识别“用了 N 个/瓶/盒”等。

即便 LLM 将其分类为 consume，执行层仍依赖精确 `target` 和当前库存；如果前面实际没有完成确认入库，或目标被错误上下文替换，就会进入 `pre_execution_checker` 的“没有找到草莓”分支。该分支只检查标题，不会提示最近批次、位置或可选候选。

## 3. 根因归纳

### P0 数据和执行一致性

- 回复层没有统一消费结构化执行结果，存在“无 mutation 仍成功回复”的风险。
- 记录数、批次数量、单位数量混用。
- 更新/消耗目标使用字符串标题，而不是先解析为稳定的 `item.id`/批次 ID。

### P0 对话状态

- 只有一个 `last_added_item` 和一个 `current_context_item`，没有 focus stack、候选集、来源轮次和待补字段。
- 省略主语的补充句没有 slot-filling：原始目标、动作和新参数没有作为 `PendingTurn` 持久化。
- `conversation_state` 固定为单行，不能按会话/家庭成员隔离。

### P1 语言与领域模型

- 保质期只接受少数正则形式，没有把“保质期 N 天”转换为绝对日期。
- 备注、容器形态、食品新鲜度等属性没有意图和字段契约。
- 消耗词表偏向“已经完成”，没有覆盖“洗一盒下午吃”“准备吃一盒”等计划性动作。
- 搜索返回的是相关性结果，不是带约束的结构化查询。

### P1 架构重复

代码同时存在 graph resolver/mutation executor 和 InventoryCapability 两套语义。前者设计了批次/FIFO/候选选择，后者常用精确匹配并取第一条；修复其中一套不一定影响实际运行路径，导致行为分叉。

## 4. 修改计划

### 阶段一：先修正确性和可测性（P0）

1. 定义统一的 `ProposedOperation`/`ExecutionResult`：每次变更必须包含 `target_item_id`、旧值、新值、数量、单位和状态（`applied/pending/rejected`）。回复只能由该结果生成；无写入不得说“已更新”。
2. 入库和消耗回复分别展示“批次数”和“总数量”，例如“新增 1 个批次，共 2 盒草莓”。
3. 所有更新/消耗先使用统一的候选解析器锁定 item ID；多候选必须 pending 确认，禁止 capability 直接取第一条。
4. 给测试增加最终数据库断言：草莓存在、`count=2`、备注含 500 克、过期日为今天+3、查询结果满足过滤、消耗后为 1 盒；同时断言牛奶未被修改。
5. 修复场景测试隔离和报告生成：每轮独立执行，异常不得复制为后续轮次，关键词不能在异常文本上判定通过。

### 阶段二：补齐多轮对话能力（P1）

1. 增加 `update_remark` 意图和 `remark` patch，定义“覆盖/追加/删除备注”语义；实现 `Item.remark` 的事务更新。
2. 增加 `PendingTurn`：保存原目标 ID/批次、原意图、已提取槽位、缺失槽位、候选项和来源轮次。用户说“每盒 500 克”“3 天”时，只补齐对应槽位，不重新猜目标。
3. 将最近焦点改为按 session 的 focus stack；查询结果只在用户明确切换焦点时覆盖操作焦点。
4. 扩展 parser：支持“保质期一般是 3 天”“3 天后过期”“洗一盒下午吃”等表达，并输出规范化的绝对日期和 `deductCount=1`。
5. 为 search query 输出结构化过滤器：`location`、`category=food`、`freshness/perishable`、`container`。向量搜索只能用于候选召回，最终必须经过过滤器。

### 阶段三：收敛架构（P1/P2）

1. 选择唯一的 mutation 主链，把 FIFO、候选确认和批次 ID 能力迁移到该链，删除或停用另一套重复执行逻辑。
2. 把 conversation state、pending confirmation、snapshot 的键改为真实 `household_id + conversation_id + user_id`，不再使用全局单行状态。
3. 为备注、容器、开封状态、提醒等领域能力补齐 schema、API、审计和回归测试；未实现能力必须明确返回“不支持”，不能生成成功话术。

## 5. 验收标准

- 五轮对话完整执行后，库存只有正确的草莓批次：2 盒入库，备注和过期日正确，牛奶数据不变。
- “冷藏层里还有别的盘装生鲜”只返回满足全部过滤条件的记录，并说明未命中的原因或缺少字段。
- “草莓洗一盒下午吃”明确扣减 1 盒；若需要确认，确认前数据库零变化，确认后草莓为 1 盒。
- 每个变更回复都包含目标、数量/单位、位置或日期，以及已执行/待确认状态。
- 同一数据库中的不同会话和家庭成员不会共享草莓焦点、pending 选择或快照。
